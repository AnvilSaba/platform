# PostgreSQL setup automation: CloudNativePG vs a custom Job

Research date: 2026-10-14 (Asia/Tokyo). Official primary sources only; recommendation is an inference from the documented contracts below. No local implementation or credentials were inspected.

## Context supplied by the parent

- k3s runs one PostgreSQL StatefulSet using the official `postgres:18.6` image, admin `platform_admin`, and PVC `postgres-data`.
- Bootstrap precreates three `NOLOGIN` runtime groups and four `LOGIN` roles, revokes `PUBLIC` CREATE on `platform`/`public`, and grants the migrator database/schema CREATE and apps CONNECT/runtime membership.
- SQLx migrations grant fine table/column privileges to the runtime groups. Deployment currently requires manual bootstrap and four `\password` commands; rotation coordinates DB ALTER, the per-service SOPS Secret (`databasePassword`), and Pod restarts.
- Release order is the migrator hook followed by app upgrades. These are parent-provided findings, not independently verified here.

## Recommendation

Prefer CloudNativePG if the requirement is **ongoing Secret-as-source-of-truth password updates**. Keep SQLx responsible for schema changes and fine grants, and retain separate runtime roles without database ownership. CNPG manages the PostgreSQL cluster itself; it is not a password controller to attach to the existing arbitrary StatefulSet. [Role management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/), [Database management](https://cloudnative-pg.io/docs/1.30/declarative_database_management/)

If scope is only removing manual initial/deploy-time setup while keeping the StatefulSet/PVC, an idempotent admin Job is the smaller change. It can consume `databasePassword` directly and create/alter roles, memberships, and base grants before SQLx runs. A Job invoked only during deployment does **not** reconcile later Secret changes; that requires an explicit trigger or a persistent controller. This is a design recommendation, not a built-in PostgreSQL image capability.

## Bootstrap is not continuous reconciliation

| Mechanism                                            | Documented behavior                                                                             | Implication                                                                                                                                                                       |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Official image env and `/docker-entrypoint-initdb.d` | Applied only with an empty data directory. Existing databases are untouched at startup.         | Updating `POSTGRES_PASSWORD` or restarting the DB Pod does not rotate existing role passwords. [Docker official README](https://hub.docker.com/_/postgres)                        |
| CNPG `postInit*SQL` / `postInit*SQLRefs`             | Queries execute once after creation, as superuser; an error interrupts bootstrap.               | Suitable for initial base grants, not ongoing credential/grant reconciliation. [Bootstrap](https://cloudnative-pg.io/docs/1.30/bootstrap/#executing-queries-after-initialization) |
| CNPG managed roles                                   | Both inline `.spec.managed.roles` and standalone `DatabaseRole` handle password Secret changes. | Declare every intended runtime/migrator role; unmanaged roles are ignored. [Role management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/)                    |
| Custom deploy-time admin Job                         | Runs when the release process invokes it.                                                       | Re-running can apply current Secret values; changes between releases need a separate trigger/controller.                                                                          |

## Secret contract and reconciliation limits

- Role `passwordSecret` references a Secret **by name**, not an arbitrary key selector. It requires type `kubernetes.io/basic-auth`, keys `username` and `password`, and a username matching the role. `DatabaseRole`, its Cluster, and its Secret must share a namespace. [Role management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/), [RoleConfiguration API](https://cloudnative-pg.io/docs/1.30/cloudnative-pg.v1/#roleconfiguration)
- Label the referenced Secret `cnpg.io/reload: "true"` for prompt password application. Unlabeled changes may wait for a later reconciliation/cache refresh; the label does not rotate arbitrary undeclared SQL roles. [Password management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#password-management)
- Existing `databasePassword` alone is insufficient. Recommendation: expose the same authoritative SOPS value as CNPG's `password` with a matching `username`, and either change the app's key reference or generate a compatible Secret. If retaining both keys, enforce equality during generation; avoid independently maintained password copies. [RoleConfiguration API](https://cloudnative-pg.io/docs/1.30/cloudnative-pg.v1/#roleconfiguration)
- Reconciliation is not uniform drift enforcement: inline roles are periodically compared with the catalog; `DatabaseRole` applies on spec/Secret changes and does not immediately undo manual SQL edits. `Database` reapplies when its generation changes, not after arbitrary manual database changes. [Role management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/), [Database caveats](https://cloudnative-pg.io/docs/1.30/declarative_database_management/#manual-changes)

## Ownership, membership, and grants

- CNPG's default bootstrap application user owns its application database. Keep that owner/admin identity separate from restricted runtime logins; ownership permits alteration/destruction of owned objects and cannot be reduced to ordinary runtime grants. [Bootstrap](https://cloudnative-pg.io/docs/1.30/bootstrap/#bootstrap-an-empty-cluster-initdb), [PostgreSQL privileges](https://www.postgresql.org/docs/18/ddl-priv.html)
- Managed roles support `login`, privilege flags, and `inRoles` membership, including updates to existing roles. Declare the three runtime groups and four logins with complete intended memberships/attributes. Adoption can reset omitted attributes and revoke omitted memberships. `createdb` means permission to create databases, not the existing migrator's database/schema CREATE grants. [RoleConfiguration API](https://cloudnative-pg.io/docs/1.30/cloudnative-pg.v1/#roleconfiguration), [Role adoption](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#removing-a-role)
- `Database.spec.owner` and schema owners are declarative, but the API is not a general database/schema/table/column ACL manager. Specific FDW/server USAGE controls do not replace application grants. Preserve base CONNECT/CREATE/REVOKE SQL and SQLx's precise table/column grants. [Database scope](https://cloudnative-pg.io/docs/1.30/declarative_database_management/#scope-of-management), [Database API](https://cloudnative-pg.io/docs/1.30/cloudnative-pg.v1/#databasespec)
- Default privileges apply only to future objects created by the relevant role, not existing objects or defaults inherited through membership. They cannot replace existing fine column grants. Preserve the release gate: roles/base grants ready, then SQLx migrations, then app upgrade. [ALTER DEFAULT PRIVILEGES](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html)

## Single instance and PostgreSQL 18

- `Cluster.spec.instances: 1` is valid (minimum/default 1). Password/role automation does not require replicas. A single instance provides no standby failover and still needs backup/recovery planning. [Cluster API](https://cloudnative-pg.io/docs/1.30/cloudnative-pg.v1/#clusterspec), [Availability guidance](https://cloudnative-pg.io/docs/1.30/faq/#database-management)
- Verified released baseline: CNPG 1.30.1; its 1.30 support matrix includes PostgreSQL 14–18. PostgreSQL's current supported majors are 14–18 and its current 18 minor is 18.6. Older CNPG pages contain stale matrices; do not infer a release from a planned date. [CNPG releases](https://github.com/cloudnative-pg/cloudnative-pg/releases), [CNPG support](https://cloudnative-pg.io/docs/1.30/supported_releases/), [PostgreSQL policy](https://www.postgresql.org/support/versioning/)
- CNPG overrides the image entrypoint with its instance manager. Its compatible image requirements and UID/GID settings must be checked; do not assume Docker initialization scripts/env remain active just because the engine stays on 18.6. Prefer a CNPG-maintained compatible 18.6 operand image. [Image requirements](https://cloudnative-pg.io/docs/1.30/container_images/), [Cluster API](https://cloudnative-pg.io/docs/1.30/cloudnative-pg.v1/#clusterspec)

## Importing the existing PostgreSQL 18 database

- Logical import bootstraps a **new** CNPG cluster using network `pg_dump`/`pg_restore`; destination tooling must be at least the source major version. PostgreSQL 18 → 18 is viable. Do not treat this as adopting `postgres-data` in place. [Import](https://cloudnative-pg.io/docs/1.30/database_import/)
- `microservice` imports one database with `--no-acl --no-owner` and imports no roles: it loses the current ownership/grant arrangement unless rebuilt. `monolith` supports one or more databases, imports selected required roles, and preserves database name/owner; reserved roles are excluded and imported SUPERUSER flags are removed. **Inference:** monolith is the better starting point for preserving this shared database's groups/logins/ACLs, followed by verification of all memberships and table/column grants. [Import modes](https://cloudnative-pg.io/docs/1.30/database_import/)
- Import needs source connectivity/backup privileges and temporary dump space. A consistent dump is not ongoing replication: plan a write freeze/final import and endpoint cutover. The alternative physical `pg_basebackup` requires matching major version/architecture/tablespaces and replication access; CNPG recommends logical import for external migrations and requires thorough physical compatibility testing. [Import](https://cloudnative-pg.io/docs/1.30/database_import/), [Physical bootstrap](https://cloudnative-pg.io/docs/1.30/bootstrap/#bootstrap-from-a-live-cluster-pg_basebackup)

## App password rotation remains coordinated

- Secret-backed environment variables do not update in a running container; restart/roll out app Pods after the database accepts the new password. `cnpg.io/reload` concerns CNPG's database reconciliation, not app Deployment restarts. [Kubernetes credential injection](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/#define-container-environment-variables-using-secret-data), [CNPG password management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#password-management)
- Normal Secret volumes update eventually; `subPath` mounts do not. File updates alone still require application credential/pool reload support. **Inference:** DB and app updates are not atomic; stale pools can fail on reconnect, so wait for DB reconciliation and coordinate rollout rather than promise seamless rotation. [Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/#using-secrets-as-files-from-a-pod)

Verification: primary-source research only. No infra edits, credentials access, live k3s tests, or migration rehearsal. Parent will run formatting. Deployment/storage compatibility, import ACL preservation, and rotation ordering remain implementation validation tasks.

## Follow-up: current database migration feasibility

**Feasible in principle:** stop-and-copy PostgreSQL 18.6 `platform` into a NEW CNPG cluster/PVCs using logical import. This is not in-place adoption of `postgres-data`, nor a guarantee of live compatibility. [CNPG logical import](https://cloudnative-pg.io/docs/1.30/database_import/)

| Import mode    | Preservation contract and fit                                                                                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `microservice` | No role import; restore uses `--no-acl --no-owner`, replacing ownership and omitting grants. Poor fit for the existing restricted-role design without explicit reconstruction. [CNPG microservice](https://cloudnative-pg.io/docs/1.30/database_import/#the-microservice-type) |
| `monolith`     | Imports selected roles and databases and retains database name/owner. Prefer for `platform`, including `platform_admin`, migrator/app logins, and all three runtime groups. [CNPG monolith](https://cloudnative-pg.io/docs/1.30/database_import/#the-monolith-type)            |

- Include every required owner/member/group role. Reserved `postgres`, `streaming_replica`, and `cnpg_pooler_pgbouncer` are excluded from import; imported roles lose `SUPERUSER`. Thus `platform_admin` must not silently remain all-powerful. Other required privileges still need review. [CNPG restrictions](https://cloudnative-pg.io/docs/1.30/database_import/#the-monolith-type)
- Ordinary restores retain object owners and grant/revoke commands unless disabled. Monolith is therefore the preservation-oriented choice, but CNPG's import guide does not individually guarantee all membership options or column ACL details; compare role memberships, database/schema/table/function owners, and table/column grants after import. [PostgreSQL restore](https://www.postgresql.org/docs/18/app-pgrestore.html)
- Import the ENTIRE database, including `public._sqlx_migrations`, `mcguildlink`, and table data; do not rebuild from migration files alone. Full dumps include non-system schemas and sequence values. Parent reports SQLx checks version/success/checksum and uses GENERATED ALWAYS AS IDENTITY: verify history rows, identity definitions, and sequence state before admitting writes. [PostgreSQL dump](https://www.postgresql.org/docs/18/app-pgdump.html)
- Preserve SECURITY DEFINER function owners and their required privileges, plus function EXECUTE grants: these functions execute with their owner's privileges. Superuser removal can change behavior even when definitions/owners survive. Parent supplied the presence of these functions; compatibility remains a rehearsal check. [PostgreSQL function security](https://www.postgresql.org/docs/18/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)
- Role-password preservation by CNPG's monolith importer is not established here. PostgreSQL role dumps can contain passwords, but `--no-role-passwords` produces NULL passwords. Plan to verify logins and apply authoritative Secrets after import; managed roles without `passwordSecret` leave existing passwords untouched unless `disablePassword` is set. [Role dump](https://www.postgresql.org/docs/18/app-pg-dumpall.html), [CNPG passwords](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#password-management)
- Safe-adoption recommendation: finish import before applying role reconciliation or competing bootstrap/admin SQL. Match bootstrap database/owner to the verified source; adopting roles can reset omitted attributes and revoke omitted memberships. Exact bootstrap/managed-role ordering and password handoff require rehearsal, not an assumed race-free sequence. [CNPG import behavior](https://cloudnative-pg.io/docs/1.30/database_import/#a-practical-example), [CNPG adoption](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#removing-a-role)

1. Before template removal, protect the chart-owned source PVC. Persist `helm.sh/resource-policy: keep` in a prior applied release and verify retention/backups; merely adding it to a template being removed is insufficient protection. Helm can delete resources during upgrade; kept resources become orphaned. This sequencing is an operational inference from Helm's contract and parent-provided ownership. [Helm retention](https://helm.sh/docs/howto/charts_tips_and_tricks/#tell-helm-not-to-uninstall-a-resource)
2. Freeze ALL source writers, including apps, scheduled jobs, and the migrator; complete the final import while writes remain stopped. A consistent dump does not capture subsequent writes. [PostgreSQL dump](https://www.postgresql.org/docs/18/app-pgdump.html)
3. Validate restored history/data/sequence state, ownership, memberships, ACLs, and authentication. Retain SQLx migrations/fine grants and keep runtime roles without database ownership. Keep the source PVC separate for rollback.
4. Parent reports `postgres.serviceName` centralizes all four app/migrator hosts: switch it to CNPG's write service, coordinate Secret consumption/Pod rollout, then resume writes. Before new writes, rollback can return to the frozen source; afterward the old PVC is stale and rollback needs data reconciliation.

Unverified: actual live catalog, importer password/membership edge cases, function privilege compatibility, bootstrap/adoption ordering, restore duration, and effective Helm/PVC retention. No runtime changes or credentials access; parent will format and own implementation/rehearsal.

## Follow-up: bootstrap implementation contracts (2026-10-15)

- CNPG v1.30.1 `ConfigureNewInstance` creates the configured application owner first, runs `postInitSQL` on `postgres`, then creates the application database and runs `postInitApplicationSQL` there. For fresh setup, explicitly create the three groups/four logins before their grants; put `platform` database/schema grants in application SQL, not SQL that runs before that database exists. Avoid duplicate CREATE ROLE for the already-created bootstrap owner. [Pinned bootstrap source](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/initdb.go#L279-L362)
- Managed roles can adopt existing roles and reconcile passwords/memberships. Do not depend on managed roles already existing inside bootstrap SQL: the inspected initdb path does not invoke their reconciliation. Exact runtime reconciliation scheduling was not checked; gate the migrator on completed role/password reconciliation. [Managed roles](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#inline-managed-roles), [Bootstrap source](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/initdb.go#L492-L507)
- `postInit*` is NOT a post-monolith hook: `ConfigureNewInstance` precedes `executeLogicalImport`; application SQL executes only if that configuration path reaches application-database creation. Recommendation: remove fresh role-creation/base-grant SQL and SQL references from the monolith migration overlay to avoid duplicate-role/import conflicts or modifying imported ACLs. `postImportApplicationSQL` is microservice-only. [Pinned execution order](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/initdb.go#L492-L507), [Import limitations](https://cloudnative-pg.io/docs/1.30/database_import/#the-monolith-type)
- Extra Secret data keys such as `token` and `authKeyword` are allowed with `kubernetes.io/basic-auth`: Kubernetes validates required authentication fields but does not restrict the map to those keys. CNPG still requires both matching `username` and `password`, plus the reload label for prompt updates. Existing Secret `type` is immutable, so converting a deployed Opaque Secret requires replacement rather than an in-place type update. [Kubernetes validation](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/apis/core/validation/validation.go#L7174-L7182), [Type immutability](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/apis/core/validation/validation.go#L7202-L7204), [CNPG password contract](https://cloudnative-pg.io/docs/1.30/declarative_role_management/#password-management)
- `ghcr.io/cloudnative-pg/postgresql:18.6-system-trixie` is a documented CNPG 1.30 default operand image; it is a valid documented image choice. No image pull or runtime validation was performed. [CNPG 1.30.1 release notes](https://cloudnative-pg.io/docs/1.30/release_notes/v1.30/), [Default image](https://cloudnative-pg.io/docs/current/)

## Follow-up: v1.30.1 membership grantor failure

- **Import alone does not solve the reported PostgreSQL 18 failure.** Monolith uses custom role/catalog cloning, not `pg_dumpall`, but still reconstructs `GRANT ... TO ... [WITH ADMIN OPTION] GRANTED BY <source grantor>`. It does NOT remap `platform_admin` to target `postgres`. Individual membership SQL errors are logged and swallowed; database import can continue with missing memberships. [Monolith call order](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/logicalimport/monolith.go#L37-L44), [Grant construction/error handling](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/logicalimport/roleinheritance.go#L55-L82)
- The importer reads role/member names, ADMIN flag, and grantor from source catalogs; it omits PostgreSQL 16+ membership INHERIT/SET flags. It filters membership endpoints to OIDs >= 16384, but not the grantor. Thus a renamed bootstrap superuser can still appear as `GRANTED BY platform_admin` for ordinary groups/logins. [Catalog query](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/logicalimport/roleinheritance.go#L85-L101)
- PostgreSQL requires the recorded membership grantor to hold ADMIN OPTION unless it is the target bootstrap superuser. A same-named ordinary target role is not that bootstrap identity; being connected as target `postgres` does not make an explicit source grantor valid. This explains the parent-reported failure. [PostgreSQL GRANT on roles](https://www.postgresql.org/docs/18/sql-grant.html#SQL-GRANT-DESCRIPTION)
- Additional exact-code correction: role cloning filters source OIDs >= 16384 and skips the configured bootstrap owner; a renamed initial bootstrap administrator is therefore NOT copied by this path. For eligible selected roles, `rolpassword` is read and emitted as PASSWORD, and SUPERUSER is cleared. This resolves the earlier password uncertainty for those roles only. [Selection/skips/demotion](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/logicalimport/role.go#L143-L232), [Password emission](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/logicalimport/role.go#L118-L124)
- **Smallest workaround, if already present in the overlay:** retain complete `.spec.managed.roles[].inRoles` for the runtime logins. The normal synchronizer uses the target superuser connection and issues plain `GRANT <group> TO <login>` without source GRANTED BY; it can repair memberships missing after import. Wait for successful role reconciliation and verify effective privileges before migrator/apps. This preserves intended ordinary membership, not original grantor history or arbitrary membership-option details. [Superuser synchronizer](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/internal/management/controller/roles/runnable.go#L121-L145), [Membership update](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/internal/management/controller/roles/postgres.go#L223-L274)
- **Overlay verdict:** native monolith alone is insufficient; monolith plus complete managed `inRoles` and a post-import reconciliation gate has a source-backed repair path for this specific failure. If those declarations/gates are absent, explicit post-import membership repair under target `postgres` is required. Do not restore SUPERUSER to `platform_admin` as the workaround. No local overlay was inspected, no implementation changed, and no CNPG/runtime test was performed; startup success alone is not evidence that memberships survived.
